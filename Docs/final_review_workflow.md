# Final Review Workflow

Use this workflow after every small change made by an AI coding tool.

## Daily workflow

1. Make one small change.
2. Run:

```bash
python3 Scripts/finish_change.py
```

For Medium or Heavy changes with an approved active spec, prefer:

```bash
python3 Scripts/finish_change.py --spec exports/active_change/CHANGE_SPEC.md
```

If the local helper supports the shortcut, this is equivalent:

```bash
python3 Scripts/finish_change.py --active-spec
```

3. Upload `FINAL_REVIEW_PACKET.md` to ChatGPT.
4. Wait for ChatGPT to approve the final review packet.
5. Run:

```bash
python3 Scripts/prepare_commit_after_review.py
```

If the local PM lifecycle helper is available, the approved-review transition
can be printed as one pasteable command block:

```bash
python3 Scripts/pm_lifecycle.py finish-approved
```

6. If the helper reports `PASS`, run the printed human-controlled `git add`, `git commit`, and `git push` commands yourself.
7. After the human commit and push are complete and `git status --short` is clean, archive and clear the completed active spec when one was used:

```bash
python3 Scripts/finalize_completed_change.py --archive-active-spec
```

8. Before selecting the next work item, apply
   `Docs/status_dashboard_refresh_protocol.md`. If dashboards still point to
   the completed work, prepare a narrow dashboard refresh before new
   implementation.

## What the script does

`Scripts/finish_change.py` creates a review packet for a human-supervised final check.

It may include:

- changed file list
- git diff
- relevant file excerpts
- safety warnings
- command outputs
- a conservative `Spec-Based Review Summary` when a `CHANGE_SPEC.md` is provided
- review instructions for ChatGPT

The spec-based summary reports the spec source path, spec ID, branch match, required metadata status, changed files compared with the positive/negative/forbidden file lists, generated `exports/` status, safety/Python/pytest/unsafe-marker status, broad-change warnings, and one advisory suggested decision:

- `AUTO-APPROVE CANDIDATE`
- `REVIEW REQUIRED`
- `BLOCK COMMIT`
- `REVERT OR EXPLAIN`

`AUTO-APPROVE CANDIDATE` means only that the machine checks found a low-risk candidate for approval. ChatGPT/human review is still required before commit.

The packet is written under:

```text
exports/final_review/<timestamp>/FINAL_REVIEW_PACKET.md
```

## What to upload

Upload only:

```text
FINAL_REVIEW_PACKET.md
```

Ask ChatGPT to review whether the change is safe, correct, and ready to commit.

When reviewing Medium or Heavy workflow changes, also ask ChatGPT to apply:

- `Docs/repo_design_principles.md`
- `Docs/review_decision_policy.md`

The review should check design-principle alignment, including whether the change keeps repository files as shared memory, preserves AI-tool-agnostic workflow, keeps Claude Code optional, avoids duplicate state or work-log systems, and remains minimal, modular, reversible, and reviewable.

When a `CHANGE_SPEC.md` is used for implementation, Codex, Cursor, Claude Code, or another implementation-side AI tool must preserve the exact received spec at:

```text
exports/active_change/CHANGE_SPEC.md
```

Before implementation, the tool must inspect `git status --short`. A clean working tree is safe to proceed. If the only pre-existing working-tree change is `HANDOFF.md` and it appears to have been generated by `Scripts/start_change.py` for the same current task, keep it, proceed, and include `HANDOFF.md` in final review. `HANDOFF.md` can be committed only after human approval. Any other tracked, untracked, staged, unstaged, deleted, renamed, or otherwise changed file must stop implementation until the human reviews the working tree.

The human should only need to give the approved spec to the implementation-side AI tool; the tool is responsible for saving or copying the active spec before implementation changes. If `exports/active_change/CHANGE_SPEC.md` already exists and matches the received spec, proceed. If it already exists and differs from the received spec, do not overwrite it silently; stop and ask the human to finalize the previous active spec or resolve the conflict before replacing it. Use `python3 Scripts/finish_change.py --spec exports/active_change/CHANGE_SPEC.md` whenever possible so the final packet includes the same spec source path, metadata, and SHA256 that guided implementation. The active spec is a temporary generated artifact under `exports/` and must not be committed.

`Scripts/start_change.py` may warn when a stale active spec exists, but it must not auto-archive or auto-delete it.

## Commit preparation after approval

`Scripts/pm_lifecycle.py` is the preferred first stop for lifecycle command
printing when the Global PM or Repo PM needs one complete pasteable terminal
block. It is print-only and preserves human-controlled Git.

Common modes:

```bash
python3 Scripts/pm_lifecycle.py finish-approved
python3 Scripts/pm_lifecycle.py finish-rejected
python3 Scripts/pm_lifecycle.py finish-blocked
python3 Scripts/pm_lifecycle.py post-merge-sync
python3 Scripts/pm_lifecycle.py next-ready
```

The helper explains the next state and prints only available helper commands.
It does not run `git add`, `git commit`, `git push`, `git pull`, branch
operations, destructive cleanup, pull request creation, or dashboard rewrites.

For rejected or blocked reviews, use the matching lifecycle mode to preserve
state and print correction or blocked-state guidance. Durable blocked-state
writing is not implemented by this first helper; record blockers in committed
status documents only through a separate approved change.

Use `Docs/status_dashboard_refresh_protocol.md` to decide whether
`CURRENT_STATUS.md`, `NEXT_ACTIONS.md`, `HANDOFF.md`, `Docs/work_queue.md`, or
active spec state needs a follow-up refresh after approval, rejection, blocking,
post-merge sync, or next-ready checks. The protocol is design guidance only; it
does not authorize automatic dashboard rewrites.

After ChatGPT approves the packet, run:

```bash
python3 Scripts/prepare_commit_after_review.py
```

The helper uses the latest packet under:

```text
exports/final_review/*/FINAL_REVIEW_PACKET.md
```

You can provide an explicit packet path when needed:

```bash
python3 Scripts/prepare_commit_after_review.py --packet PATH_TO_FINAL_REVIEW_PACKET.md
```

The helper may remove generated `exports/` content, but only after safety guards pass. Cleanup is blocked if any tracked file exists under `exports/`, if `exports/` is listed as an intended commit candidate path, if Git shows tracked changes under `exports/`, or if the export content does not look like known generated review/output content.

For a Medium or Heavy spec-first task that used `exports/active_change/CHANGE_SPEC.md`, run commit preparation with `--no-clean` when you want to archive that active spec after commit and push:

```bash
python3 Scripts/prepare_commit_after_review.py --no-clean
```

Without `--no-clean`, successful generated-export cleanup may remove `exports/active_change/CHANGE_SPEC.md` before the post-commit finalize helper can archive it.

The helper compares current changed files against the packet's `Intended commit candidate paths` line. If that line is missing, it falls back to the packet's `Changed Files` section and reports the fallback. Unexpected non-export changes block the ready-to-commit recommendation.

The helper runs:

```bash
git diff --check
git diff --cached --check
python3 Scripts/run_safety_check.py
```

Final Git actions remain human-controlled. The helper prints suggested commands, but it does not run `git add`, `git commit`, `git push`, `git pull`, `git fetch`, switch branches, create pull requests, or upload anything.

When it prints ready-to-commit commands and `exports/active_change/CHANGE_SPEC.md` is still present, it also prints a post-commit reminder for:

```bash
python3 Scripts/finalize_completed_change.py --archive-active-spec
```

That reminder is informational. `Scripts/prepare_commit_after_review.py` does not run the finalize helper automatically. If generated exports were already cleaned, the helper prints a note instead of a misleading finalize command.

Use `--no-clean` to check readiness without removing generated exports:

```bash
python3 Scripts/prepare_commit_after_review.py --no-clean
```

## Completed active-spec finalization

Use the finalize helper only after implementation is complete, final review has been generated from the active spec, ChatGPT or human review has approved the change, `prepare_commit_after_review.py` has printed safe human-controlled Git commands, the human has committed and pushed, and `git status --short` is clean.

The helper archives `exports/active_change/CHANGE_SPEC.md` under `exports/archived_change_specs/`, copies the latest final review packet when one is available, writes a manifest, removes only `exports/active_change/CHANGE_SPEC.md`, and removes `exports/active_change/` only if it is an empty normal directory.

It refuses to run when the working tree is dirty, when the active spec is tracked by Git, or when active-spec paths are unsafe. It does not stage, commit, push, pull, fetch, switch branches, create pull requests, upload content, or broadly clean `exports/`.

## Rules

- Keep each change small.
- Do not commit before final approval.
- Do not commit review packets or files under `exports/`.
- Do not include raw data, images, PDFs, papers, or private research files in review packets.
- Repository content must be English-only.
- Final review verdicts should follow `Docs/review_decision_policy.md`.
