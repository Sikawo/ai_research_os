# Core Workflow

> **SHARED CORE** — canonical source: `ai_research_os/shared_core`. Do NOT edit in a
> downstream repo. Edit only in `ai_research_os`, then re-sync. Version: 2026-05-22.

Source: consolidated from `AGENTS.md` (default workflow), `Docs/final_review_workflow.md`,
and `Templates/change_spec_template.md`. No new policy is introduced here.

## Spec-first workflow

For Medium and Heavy changes, work from an approved `CHANGE_SPEC.md`.

1. Define one small change, or obtain an approved `CHANGE_SPEC.md`.
2. Before implementation, the implementation-side AI tool inspects
   `git status --short`. A clean working tree is safe to proceed. If the only
   pre-existing working-tree change is `HANDOFF.md` and it appears to have been
   generated by `Scripts/start_change.py` for the same current task, keep it,
   proceed, and include `HANDOFF.md` in final review. If any other tracked,
   untracked, staged, unstaged, deleted, renamed, or otherwise changed file is
   present, stop and ask the human to review the working tree before
   implementation.
3. The implementation-side AI tool preserves the exact received spec at
   `exports/active_change/CHANGE_SPEC.md` before making implementation changes.
   If an active spec already exists and matches the received spec, proceed. If
   it exists and differs from the received spec, do not overwrite it silently;
   stop and ask the human for confirmation before replacing it.
4. Implement only the approved scope. Stay inside the positive file list; ask
   before touching negative-list files; stop if forbidden files or protected
   data would be involved.
5. Run validation: `python3 Scripts/run_safety_check.py`, `python3 -m pytest`
   when relevant, and any spec-specified checks.
6. Generate the review packet:
   `python3 Scripts/finish_change.py --spec exports/active_change/CHANGE_SPEC.md`
   (or `--active-spec` if supported). Light changes may use
   `python3 Scripts/finish_change.py`.
7. Have the human review `FINAL_REVIEW_PACKET.md` (uploaded to ChatGPT when an
   independent review is wanted) before any commit.
8. After approval, run `python3 Scripts/prepare_commit_after_review.py`, then the
   human runs the printed `git add`, `git commit`, and `git push` commands.
9. After the human commit and push are complete and `git status --short` is
   clean, the human may archive and clear the completed active spec with
   `python3 Scripts/finalize_completed_change.py --archive-active-spec`.

## Recommended execution settings in specs

Generated `CHANGE_SPEC.md` files for Medium and Heavy work should include a
top-level `Recommended AI execution settings` section. The section should cover
task classification, Codex/Cursor guidance, and Claude Code guidance, including
model category, reasoning or effort level, speed or permission mode, workspace
mode, permission boundaries, and when to ask the human or escalate.

These recommendations are advisory only. They never override the active
`CHANGE_SPEC.md`, command permission policy, positive/negative/forbidden file
lists, repository-specific safety boundaries, final review, or
human-controlled Git.

## Active spec is temporary

`exports/active_change/CHANGE_SPEC.md` and all generated `exports/` content are
temporary artifacts. They must not be committed.

If an active spec already exists and differs from the received spec, do not
replace it silently. Stop and ask the human to resolve the conflict. The
finalize helper is only for completed work after final review approval, human
commit, human push, and a clean working tree; it must not auto-run from
`Scripts/start_change.py` or `Scripts/prepare_commit_after_review.py`.

## Handoff

Update `HANDOFF.md` before stopping work or moving to another thread, tool, or
computer (preferably via its generator `python3 Scripts/handoff.py`). Do not
create a parallel status/log system. Keep it text-only and free of raw data,
image context, quantification outputs, local absolute paths, secrets, and
private details. `HANDOFF.md` remains part of final review and can be committed
only after human approval.

## Final review is the gate

`Scripts/finish_change.py` is the default final review gate. Do not treat a
change as ready to commit until `FINAL_REVIEW_PACKET.md` has been reviewed and
approved. Final verdicts follow `CORE_REVIEW_POLICY.md`.
