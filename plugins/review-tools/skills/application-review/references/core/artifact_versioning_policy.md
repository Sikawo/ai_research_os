# Application Artifact Versioning and Authority Policy

## Purpose

Apply this policy whenever Sprint or an approved GatedSprint Phase 4 creates or
revises an application artifact. It adapts the repository-root
`Working_File_Versioning_Convention.md` to application work: one explicitly
adopted current version group remains directly under the user-designated working
parent, and superseded groups remain under `previous/`.

This policy governs working artifacts, not GitHub workflow instructions. Read
the current repository entrypoint and relevant context/profile on each run and
record the repository path and commit/ref used. Do not upload unpublished
application drafts or reference letters into the instructions repository by
default.

## Required authority register

Before strategic review, editing, layout review, or promotion, record these
fields separately for every logical family:

- `working_parent` and logical `family`;
- current source identity and source fingerprint;
- `content_authority`;
- `layout_authority`;
- `editable_target`;
- `version_equivalence` for companion formats;
- user designation: `current`, `candidate`, `submitted`, or `final`;
- selected storage backend and persistent `previous/` location; and
- optional independent backup location.

Do not substitute one field for another. A file can be the editable target
without being layout authority, and folder-current status does not prove that a
file is submission-verified.

### Content and layout rules

- A user-designated current, submitted, or final PDF is layout authority.
- A PDF generated by a tool from DOCX is only a preview until equivalence and
  layout are verified against the user's actual export. Label it
  `PREVIEW_NON_AUTHORITATIVE`.
- A DOCX-only route can support authorized content editing. Layout remains
  `NOT_ASSESSABLE` when the only rendered output is an unverified preview.
- Companion DOCX and PDF files may share a token only after their substantive
  equivalence is verified. Content-divergent formats require distinct version
  identities and may not be silently combined for content and layout review.
- When the user explicitly designates a submitted or final PDF, it controls the
  final artifact review. Any dependent editable-source assumption that is not
  demonstrably equivalent becomes stale or unresolved.
- Any edit after verification creates a new unverified candidate. Release may
  be claimed only after inspecting the exact artifact to be delivered.

## One-time project setup

For each authorized logical family, resolve a user-designated working parent and
record the current group. New checkpoints use either
`<family>__YYYYMMDD-HHmmssZ.<ext>` in UTC or
`<family>__<semantic-version>.<ext>`. Superseded files belong in
`<working parent>/previous/`; review packets and submission copies may use
separate project-designated locations when required.

Do not create or overwrite a fixed `Current` filename. If a pre-convention
unversioned file is the current baseline, preserve its name and bytes as the
documented legacy exception. When a verified versioned successor is promoted,
move the legacy baseline unchanged to `previous/`.

## Storage backend selection

This workflow is provider-neutral. Record only portable bindings: backend kind,
working parent, `previous/`, optional review/submission destinations, user
timezone for display, and optional **independent** backup locator. Naming
timestamps remain UTC. Do not put credentials or unpublished document contents
in repository configuration.

Supported patterns depend on current permissions and operations:

| Backend | Access route | Versioning action |
| --- | --- | --- |
| Local or locally synced folder | Authorized local workspace with the files downloaded and writable | Create and verify a new versioned candidate, rescan, then move the former current group unchanged to `previous/`. |
| Connected cloud file store | Authorized connector that supports create/copy/move and verification for the actual file type | Use distinct versioned identities; update the recorded current designation only after candidate verification and safe archival. |
| ChatGPT Library or equivalent durable store | Authorized artifact operations when available | Preserve distinct version identities and a separate superseded group when supported; report any operation the backend cannot perform. |

A synchronized folder is one replicated store, not an independent backup. A
provider's version history is useful but does not replace the required distinct
checkpoint when this convention applies. Never claim backend support, sync
completion, retention, or an independent backup without verifying it.

Web/cloud work cannot directly access an arbitrary folder on the user's
computer. Do not treat a temporary session directory as durable storage. If the
selected backend is unavailable or lacks safe operations, leave the former
current group intact, create a uniquely named downloadable candidate when
authorized, and report that promotion is pending.

## Selecting the current group

Choose the current group from explicit user designation or a unique durable
project record. Never select it from modification time alone. A newly uploaded
older file does not silently supersede the registered source. If several files
are plausible, formats diverge, or the recorded identity no longer matches,
make no moves and resolve the ambiguity first.

Manual editors follow the same rule: Save As or duplicate-first for every
meaningful checkpoint, verify the candidate, archive the superseded root group,
then promote and confirm the candidate.

## GatedSprint lifecycle

- **Phase 1:** Read only authorized sources and workflow instructions. Register
  the authority fields and source fingerprint. Produce a version-identified
  approval packet; do not create a revised application file or promote a
  candidate.
- **Phases 2–3:** Bind decisions to the exact current source. If the source
  changes, invalidate stale layout/equivalence assumptions and reconcile the
  approved plan before implementation. The Phase 3 receipt must name the
  working parent, folder-level authority, stable family/derivative stems,
  current root group and fingerprints, proposed token and candidate paths,
  companion formats/equivalence, outgoing derivative group, and exact archive
  plan.
- **Phase 4:** Create a new, non-colliding versioned candidate from the frozen
  implementation baseline. Apply only authorized changes, validate content and
  any assessable rendered layout, and verify the candidate identity. Rescan the
  working parent and `previous/` immediately before promotion. Stop when an
  editor lock, partial export, sync-conflict copy, unexpected candidate,
  changed predecessor, or archive-path collision makes the plan unsafe. Only
  then move the former current group—including stale old-token derivatives
  unless explicitly retained as independently current—unchanged to `previous/`
  and mark the candidate current. Never overwrite, delete, or automatically
  rename either group.
- **Release:** Inspect the exact final artifact and bind verification to its
  identity or hash. A later edit or export creates a new unverified candidate.

Ordinary Sprint uses the same safe promotion sequence within its existing
automatic-edit authority. Read-only review and wording suggestions do not
create gratuitous copies.

If validation, rescan, archival, or final verification fails, preserve all
existing files, report the exact state and recovery path, and do not mark the
run complete.

## Promotion preflight and partial-failure semantics

Treat each version group as one planned transaction even when the storage
backend cannot make the move atomic.

1. Enumerate every incoming and outgoing companion and derivative before any
   move. A clean copy, redline, or review copy with the outgoing token is part
   of the outgoing group unless it has been explicitly designated as a
   separately current family.
2. Verify the candidate, companion equivalence, predecessor fingerprints, root
   membership, and every intended archive destination immediately before
   promotion.
3. Treat editor lock files, partial exports, sync-conflict copies, unexpected
   candidates, changed predecessors, and unresolved same-family ambiguity as
   hard preflight stops. Do not infer safety from modification times.
4. If an archive destination already exists, do not use the candidate collision
   naming rule to rewrite history. Do not overwrite or auto-rename either file;
   preserve the current state and require explicit resolution.
5. If a multi-file promotion succeeds only partly, do not retry, roll back,
   delete, rename, or move more files automatically. Verify both locations,
   preserve the observed partial state, and report exact completed/pending
   paths plus a bounded recovery plan.

Content verification and folder promotion are independent. A candidate may be
content-`VERIFIED` while folder promotion is incomplete; a root-current file
may remain release-`UNVERIFIED`.

## Promotion and audit record

Follow the root convention's verify-before-archive sequence and record:

- source identity/fingerprint and former current group;
- candidate identity/fingerprint and validation result;
- content authority, layout authority, editable target, and equivalence status;
- approved decision IDs or bounded scope plus a concise summary;
- workflow paths and commit/ref used;
- archive destination and post-move verification;
- exact promoted, archived, pending, and unexpectedly present paths;
- preflight result for locks, partial exports, sync-conflict copies, archive
  collisions, predecessor drift, and derivative-group completeness;
- partial-operation status and recovery action, without an automatic retry;
- independent-backup status: verified, not configured, or pending;
- folder-current status; and
- exact-final-artifact verification status.

Return links to the current and archived groups when the backend safely supports
links. Do not export every intermediate file to the user's device unless
requested or required by a defined submission/backup milestone.
