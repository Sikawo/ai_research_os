# Change Spec

Use this template for Medium and Heavy changes. Save it as a `CHANGE_SPEC.md` file that can be given to the implementation AI tool and later included in final review.

If the chat interface supports file creation, provide long artifacts as downloadable files instead of relying only on code blocks. If a code block is also shown, keep it secondary. Long artifacts include `CHANGE_SPEC.md`, `doc_sync.patch`, long prompts, review templates, `FINAL_REVIEW_PACKET.md`-derived templates, and other long Markdown, patch, or text outputs.

When asking an AI chat interface to create a spec, request a downloadable `CHANGE_SPEC.md` file whenever possible, not only inline Markdown in chat. If the chat system cannot create a downloadable file, use one clean Markdown code block with no nested broken fences as the fallback. The preferred output remains a downloadable `CHANGE_SPEC.md` file.

When Codex, Cursor, Claude Code, or another implementation-side AI tool receives the approved `CHANGE_SPEC.md`, its instructions must require it to save or copy the exact received spec to:

```text
exports/active_change/CHANGE_SPEC.md
```

Before making implementation changes, the tool must inspect `git status --short`. If the working tree is clean, proceed. If the only pre-existing working-tree change is `HANDOFF.md` and it appears to have been generated by `Scripts/start_change.py` for the same current task, keep it, proceed, and include `HANDOFF.md` in final review. `HANDOFF.md` can be committed only after human approval. If any other tracked, untracked, staged, unstaged, deleted, renamed, or otherwise changed file is present, stop and ask the human to review the working tree before implementation.

If `exports/active_change/CHANGE_SPEC.md` already exists and matches the received spec, proceed. If it already exists and differs from the received spec, do not overwrite it silently; stop and ask the human to finalize the previous active spec or resolve the conflict before replacing it. The human should only need to give the approved `CHANGE_SPEC.md` to the implementation-side AI tool; the tool is responsible for preserving the active copy. The active spec is a temporary `exports/` artifact and must not be committed.

After final review approval, human commit, human push, and a clean working tree, the completed active spec may be archived and cleared with:

```bash
python3 Scripts/finalize_completed_change.py --archive-active-spec
```

That helper is for completed work only. It must not be used to replace an active spec before implementation or review is finished.

Light changes may use a shorter inline spec when the user and reviewer agree the scope is narrow and easy to inspect.

For Medium and Heavy changes, include a small handoff expectation when work may continue later in another thread, another tool, or another computer: update `HANDOFF.md` before stopping and mention the latest relevant packet path and next recommended action.

For implementation-side command permissions, include the policy below in generated specs or adapt it narrowly for the task.

Allowed without extra human confirmation when staying within the approved spec:

- `git status`
- `git status --short`
- `git diff`
- `git diff --check`
- `git diff --cached --check`
- `git branch --show-current`
- `git log --oneline -5`
- `mkdir -p exports/active_change`
- saving or copying the received `CHANGE_SPEC.md` to `exports/active_change/CHANGE_SPEC.md` after confirming there is no different active spec already present
- proceeding with implementation when the only pre-existing working-tree change is `HANDOFF.md` generated by `Scripts/start_change.py` for the same current task
- `python3 Scripts/finalize_completed_change.py --archive-active-spec` only after final review approval, human commit, human push, and a clean working tree
- Python syntax checks such as `python3 -m py_compile ...`
- `python3 Scripts/run_safety_check.py`
- `python3 -m pytest`
- `python3 Scripts/finish_change.py --spec exports/active_change/CHANGE_SPEC.md`
- `python3 Scripts/finish_change.py --active-spec`, if supported

Ask first before modifying files outside the positive file list, adding files not mentioned in the spec, continuing implementation when `git status --short` shows any pre-existing change other than same-task `HANDOFF.md` generated by `Scripts/start_change.py`, replacing a different existing `exports/active_change/CHANGE_SPEC.md`, changing tests beyond task scope, changing `.gitignore`, changing dependencies or lockfiles, running long/network-dependent/destructive commands, or changing security, external AI, active-spec finalization, or review workflow behavior beyond the current spec.

Forbidden unless explicitly approved in the active spec: `git add`, `git commit`, `git push`, opening pull requests, `git reset --hard`, `git clean`, `rm -rf`, deleting/moving/renaming files, branch creation, branch switching, branch deletion, uploading repository contents, sending repository contents to external AI tools automatically, committing generated `exports/`, or touching raw data, papers, images, PDFs, notebooks, secrets, credentials, tokens, or local workspace state files.

## Recommended AI execution settings

These recommendations are advisory only. They do not expand the approved file scope or command permissions. The active `CHANGE_SPEC.md`, command permission policy, positive/negative/forbidden file lists, repository-specific safety boundaries, final review, and human-controlled Git policy override all model, reasoning, effort, speed, workspace, and permission recommendations.

### Task classification

- Task type: choose the closest match, such as docs-only/template wording, small bugfix, test-only change, CLI/script behavior change, workflow/safety/review policy change, shared-core or cross-repo sync change, broad refactor/migration, or private-data-risk change.
- Change class: Light, Medium, or Heavy.
- Data/safety risk: low, moderate, or high.
- Cross-repo/shared-core risk: low unless shared governance or downstream repository sync is involved.

### Codex / Cursor

- Recommended model: use a coding model strong enough for the change class and safety risk.
- Reasoning level: low or medium for narrow docs/test changes; high for workflow, safety, shared-core, migration, or private-data-risk changes.
- Speed: careful/default for safety-sensitive or shared workflow changes; faster modes only for narrow, low-risk edits.
- Local workspace mode: local repository workspace only unless the spec explicitly approves another mode.
- Permission boundaries: stay inside the positive file list; ask before negative-list or out-of-scope files; never touch forbidden files or protected data.
- When to ask or escalate: dirty working tree outside allowed same-task `HANDOFF.md`, different active spec, unclear file scope, protected content risk, dependency/settings changes, or behavior that would weaken repository policy.

### Claude Code

- Recommended model: Sonnet for focused script/template/test edits; Opus if available for shared-core, cross-repo, safety-policy, migration, or ambiguous design decisions.
- Effort / thinking level: medium for narrow low-risk edits; high for workflow, safety, shared-core, cross-repo, migration, or private-data-risk changes.
- Permission mode: plan/default modes; do not use bypass or dangerous permission modes.
- Sonnet vs Opus guidance: use Sonnet for implementation mechanics; use Opus when reconciling policy wording, repository drift, or helper behavior that could archive or clear the wrong artifact.
- Permission boundaries: keep Git actions human-controlled, preserve active-spec replacement protection, and do not upload repository content or inspect protected files.
- When to ask or escalate: active spec conflict, unexpected working-tree state, unsafe path/symlink behavior, protected data risk, or any need to weaken existing safety policy.

## Review intensity by change class

- **Light**: inline spec acceptable; single review-change run; APPROVE verdict
  sufficient to proceed.
- **Medium**: full CHANGE_SPEC.md required; review-change run against active
  spec; every concern must be classified as blocking or non-blocking.
- **Heavy**: full CHANGE_SPEC.md required; independent review session; APPROVE
  verdict must explicitly address all design-intent criteria from the spec.

## Goal

Describe the change to make and why it is needed.

## Design intent

Describe how this change preserves the repository design principles.

At minimum, confirm whether the change:

- keeps the workflow AI-tool agnostic
- treats repository files as durable shared memory
- keeps Claude Code as an optional adapter, not source of truth
- keeps final Git actions human-controlled
- avoids raw/private/restricted data exposure
- follows spec-first implementation
- requires final review before commit
- stays minimal, modular, reversible, and reviewable
- avoids duplicate state, memory, or work-log systems

## Expected behavior

Describe what should be different after the change.

Include user-facing behavior, generated output, documentation behavior, or script behavior as applicable.

## Out of scope

- Do not include unrelated cleanup.
- Do not change safety rules unless this spec explicitly approves that work.
- Do not add staging, commit, push, pull request, or external automation unless this spec explicitly approves that work.

## Instructions for Codex or Cursor

Implement only this approved `CHANGE_SPEC.md`.

Before making implementation changes:

1. Confirm the repository and current branch match the spec.
2. Run `git status --short`.
3. If the working tree is clean, proceed.
4. If the only pre-existing working-tree change is `HANDOFF.md` and it appears to have been generated by `Scripts/start_change.py` for this same current task, keep it, proceed, and include `HANDOFF.md` in final review.
5. If any other pre-existing tracked, untracked, staged, unstaged, deleted, renamed, or otherwise changed file is present, stop and ask the human for review before implementation.
6. If `exports/active_change/CHANGE_SPEC.md` already exists and matches the received spec, proceed.
7. If `exports/active_change/CHANGE_SPEC.md` already exists and differs from the received spec, do not overwrite it silently. Stop and ask the human to finalize the previous active spec or resolve the conflict before replacing it.
8. If the active spec path is absent or has been confirmed safe to replace, save or copy the exact received spec to `exports/active_change/CHANGE_SPEC.md`. This is the implementation-side AI tool's responsibility, not an extra manual terminal step for the human.

Use the positive, negative, and forbidden file lists as the implementation boundary. Keep the change focused and practical. Do not modify files outside the approved scope unless the user explicitly updates this spec.

Do not read, move, rename, delete, rewrite, stage, commit, push, or open a pull request unless this spec explicitly approves that action.

Do not send repository contents to external AI tools automatically. Do not include raw data, secrets, credentials, tokens, private keys, or `.env` content in generated review packets or summaries.

After implementation, run the validation commands above. If validation creates generated review exports, leave final cleanup and Git actions under human control unless the user explicitly asks otherwise.

For Medium and Heavy changes, update `HANDOFF.md` before stopping work or handing work back to the user, especially when the work may continue later in another thread, another tool, or another computer.

## Instructions for ChatGPT Final Review

Review the generated `FINAL_REVIEW_PACKET.md` against this exact `CHANGE_SPEC.md`. When possible, run final review with `python3 Scripts/finish_change.py --spec exports/active_change/CHANGE_SPEC.md` so the packet uses the fixed active spec path.

Answer these questions clearly:

1. Is the change safe to commit?
2. Did the implementation stay within the positive file list?
3. Were any negative-list files changed, and was the reason justified?
4. Were any forbidden files or paths read, changed, exported, summarized, staged, committed, pushed, or otherwise touched?
5. Does the final review packet show the spec source path, spec ID if present, spec SHA256, target repo if present, expected branch if present, current branch, task if present, and created-for / change class if present?
6. Does the final review packet warn clearly if the expected branch does not match the current branch?
7. Did the actual diff match the expected behavior?
8. Did the change preserve AI-tool-agnostic workflow and keep Claude Code optional?
9. Did the change avoid duplicate memory, status, or work-log systems?
10. Did the change remain minimal, modular, reversible, and reviewable?
11. Were raw data, local absolute paths, secrets, credentials, tokens, generated exports, images, PDFs, notebooks, or unrelated research files introduced?
12. Did validation pass?
13. Should the user approve, request changes, block the commit, or require a revert or explanation?

Use one of these final verdict labels:

- `APPROVE`: the change matches the spec, validation passed, and it is safe for the human to commit.
- `REQUEST CHANGES`: the change is close, but needs a focused correction before commit.
- `BLOCK COMMIT`: the change violates safety rules, touches forbidden scope, leaks sensitive content, or has serious validation failures.
- `REVERT OR EXPLAIN`: unexpected files or behavior appeared and must be reverted or explained before review can continue.

If approving, provide the exact safe commit command sequence, but keep final `git add`, `git commit`, and `git push` human-controlled.

## Safety notes

Treat the file-scope lists above as both human/spec guidance and input to the conservative `Spec-Based Review Summary` generated by `Scripts/finish_change.py` when a spec is provided. The summary is advisory only; final approval and all Git actions remain human-controlled.
